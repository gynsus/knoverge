# Internationalisation

## 1. Principle

Knoverge is an English-first project for an English-speaking audience. Everything a developer or an AI agent reads is English. Everything a human end user reads in the product is translatable.

Russian is the first translation.

## 2. What is English only

- source code, identifiers, comments;
- commit messages, pull requests, issues;
- all documentation under `docs/` (canonical);
- ADRs;
- MCP tool names, descriptions, prompts, resources;
- error codes and error `message` fields returned to agents;
- log messages;
- configuration keys and CLI flags;
- generated repository `README.md` inside workspace repositories;
- database schema.

## 3. What is translated

- every string in the web UI;
- human-facing messages produced by the server: digest text, notification/webhook payload titles, invitation text, UI-facing validation messages;
- CLI output intended for humans (later; English until then);
- user-facing documentation (README, deployment guide, user guide), as separate translated files.

## 4. Web UI mechanism

- i18next with `react-i18next`;
- catalogues in `apps/web/src/locales/<lang>/<namespace>.json`;
- English (`en`) is the source; keys are stable English-based identifiers (`review.inbox.empty`), not the English text itself;
- i18next's native message format: `{{name}}` interpolation and plural suffixes (`key_one`, `key_few`, `key_many`, `key_other`) resolved through `Intl.PluralRules`, which covers Russian plural categories. The catalogue check compares keys with the plural category stripped, and checks each locale's categories against `Intl.PluralRules` for that language, so a correct Russian `_few` is not reported as a key English lacks. Dates and numbers are formatted with `Intl` through the `i18n.language`;
- the active locale comes from the user's profile (`User.locale`), falling back to the browser language, then `en`;
- a CI check (`apps/web/scripts/check-locales.mjs`, part of `pnpm lint`) fails when any locale is missing keys present in `en` or has keys `en` lacks;
- no string literal shown to the user may bypass the catalogue, including the ones only a screen reader speaks, such as `aria-label`, `alt`, `placeholder` and `title`; `eslint-plugin-i18next` (`no-literal-string`) covers JSX text and a `no-restricted-syntax` rule covers those attributes, both in `apps/web`;
- the chosen locale is remembered per browser under the `knoverge.locale` key; the user profile locale takes over when profile editing ships;
- API error codes are translated through `errors.<CODE>` keys, so the server never sends user-facing text (see `ErrorNotice`).

## 5. Server-side messages

Server code that produces human-facing text (digests, notifications, UI validation) returns a message key plus parameters:

```json
{ "key": "proposal.rejected.notice", "params": { "title": "Authentication strategy" } }
```

The web UI renders it through the same catalogues. Where the server itself must render text (webhook payloads, later email), it uses a server-side catalogue in `packages/contracts/locales/` with the same keys and the recipient's locale.

Agent-facing responses never carry translated text.

## 6. Knowledge content language

Knowledge items carry `language` (BCP 47 primary subtag). It is not a UI concern; it drives:

- PostgreSQL FTS configuration (`english`, `russian`, otherwise `simple`), always combined with `unaccent`;
- trigram matching, which is language-agnostic;
- multilingual embedding models, which need no special handling.

A workspace has `default_language`. Proposals may omit `language`; the server then uses simple heuristics (script detection) or the default.

## 7. Documentation translations

```text
docs/                 English, canonical
docs/i18n/ru/         Russian translations of user-facing docs only
README.ru.md          Russian README
```

Translated docs state the commit or version they were translated from. Engineering specifications (`ARCHITECTURE.md`, `DATA_MODEL.md`, ADRs, and so on) are not translated.

## 8. Adding a language

1. add `apps/web/src/locales/<lang>/` by copying `en`;
2. translate;
3. add the language to the supported list in the web app and to `User.locale` validation;
4. add `README.<lang>.md` and `docs/i18n/<lang>/` if desired;
5. add the FTS configuration mapping if PostgreSQL provides one for that language.
